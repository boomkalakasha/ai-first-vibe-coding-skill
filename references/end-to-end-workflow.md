## 0. 先判断任务等级

不要让所有任务都套用完整流程，也不要把系统级任务压缩成几句泛化建议。先按影响范围分级：

| 等级 | 判断条件 | 默认工作方式 |
|---|---|---|
| L0 轻量 | 单文件、单文案、低风险、无运行态和数据语义变化 | 短方案 → 修改 → 最小验证 → 简短交付 |
| L1 模块 | 一个页面/接口/组件或一个明确数据链路 | 盘点 → Spec-lite → 实现 → 用户路径和接口验证 |
| L2 业务系统 | 多页面、多接口、数据状态、角色、对象边界或跨模块流程 | 执行本文件的完整 0～12 阶段 |
| L3 多轮演进 | 任务先达到 L2，且用户要求全面审查、多轮迭代、自动闭环或再复盘优化；仅“先方案”不足以升级 | L2 完整流程作为第 1 轮；根据评估方案再执行两轮，或按用户指定轮数执行 |

出现以下任一表达，默认至少按 L2 处理：

- 应用地图、核心业务、业务边界；
- 详细 Spec、用户故事、测试 Case；
- 需求业务角度审查；
- 按方案分模块实现；
- 启动项目回测、按用户路径验收；
- 交互友好性、业务功能价值实现度；
- 根据评估结果再优化、再迭代、再跑一轮；
- POC 到生产、跨系统数据流、数据质量、热部署或跨页面链路。

## 1. 任务启动和安全边界

### 1.1 先回答五个问题

1. 用户真正要改善的是哪条工作路径或哪种业务决策？
2. 哪些对象、状态、指标和动作属于本次范围？
3. 用户已经提供了哪些运行环境、URL、数据和不可触碰边界？
4. 什么结果可以被事实证明，什么结果只能由人工确认？
5. 哪些动作会写入、重启、覆盖、同步、删除或影响其他用户？

### 1.2 建立任务基线

记录：

- 最近作用域内的 `AGENTS.md`、README、规则文件、现有 PRD 和方案；
- 当前分支、脏文件、用户已有改动和不可覆盖目录；
- 前端 URL、后端地址、端口、健康状态、进程/日志/热部署边界；
- 数据源、任务 ID、时间范围、数据库事实表和已存在的残留候选；
- 本轮开始时间、运行版本和验证环境。

服务已运行时，默认不重启。先使用当前实例和热部署事实；没有热部署证据时，把源码变化标为 `STATIC_PASS_PENDING_RUNTIME`，不能当成线上已生效。

### 1.3 复杂任务的初始产物

L2/L3 任务在代码修改前，至少建立：

- `00-task-baseline.md`：目标、范围、环境、脏文件和限制；可套用 `templates/task-baseline.md`；
- `00-decision-log.md`：重要业务决策、冲突取舍和新增假设；可套用 `templates/decision-log.md`；
- 一份任务计划：阶段、负责人、依赖、状态和放行条件。

## 2. 应用地图、核心业务和边界

这是需求建模的第一份正式产物，不是功能清单。它回答“系统由哪些业务域组成、谁在什么时候使用什么对象、对象之间如何晋级”。

### 2.1 必须描述

- 角色地图：业务负责人、操作人员、数据治理人员、管理员、外部协作者；
- 应用/页面/API/任务/数据表地图；
- 用户从发现到决策的黄金业务链；
- 正式对象、候选对象、阶段凭证、外部输入、AI 参考、任务、统计快照的唯一边界；
- 状态轴：对象、证据、身份、类型、动作、任务、同步、统计；
- 角色之间的责任边界和审批/人工确认点；
- 允许动作、阻断动作和阻断后的下一步；
- REAL、HYBRID、DEMO、PLANNED 能力边界；
- 本次明确不做的业务域。

### 2.2 边界表达规则

- “有一条记录”不等于“对象已确认”；
- “AI 输出分数”不等于“人工已做决定”；
- “任务完成”不等于“结果已回流”；
- “接口返回 200”不等于“业务动作完成”；
- “按钮可点击”不等于“生产闭环已实现”；
- 业务字段冲突要显式标记，不能用默认值或静默兜底消除。

产物建议命名为：

```text
01-application-map-and-boundaries.md
```

## 3. 详细业务 Spec

Spec 必须能指导实现和验收，不只是把 PRD 改写成技术名词。

### 3.1 每个业务对象至少写清

| 内容 | 要回答的问题 |
|---|---|
| 对象身份 | 它是什么，不能代替什么对象 |
| 来源 | 哪些来源可以创建/补充它，如何追溯 |
| 字段语义 | 每个编号、角色、金额、时间、类型字段代表什么 |
| 状态 | 状态值、进入条件、退出条件、是否人工确认 |
| 前置条件 | 什么时候可以查看、创建、关联、改变状态、同步或升级 |
| 动作结果 | 成功后产生什么事实，是否可重复，谁能看到 |
| 空态/失败 | 无数据、失败、未知、过期、无分母分别怎么表达 |
| 角色 | 谁可以看、谁可以改、谁可以确认、谁可以撤销 |
| 统计 | 对象、范围、截至时间、分子、分母和时间窗口 |
| 幂等/回滚 | 重复提交或中断时如何避免重复、覆盖和半成功 |
| 能力边界 | REAL、HYBRID、DEMO、PLANNED 的业务含义 |

### 3.2 写黄金链路

用“输入 → 判断 → 动作 → 输出 → 下一步”写至少一条真实用户路径。对每个高等级动作增加统一闸门，例如：

```text
对象身份有效
→ 来源和证据足够
→ 主体/角色/类型无影响动作的冲突
→ 上下文 projectId 有效
→ 人工确认点完成
→ 执行动作
→ 返回结果、操作者、时间和下一步
```

### 3.3 状态语义要可区分

至少区分：

- `EMPTY`：查询成功但确实没有数据；
- `UNKNOWN`：失败或当前不能判断；
- `NO_DENOMINATOR`：没有分母，不计算比例；
- `STALE`：数据存在但超过有效时间；
- `PENDING_REVIEW`：已发现但需人工核验；
- `CONFLICT_PENDING_REVIEW`：发现会影响业务动作的冲突；
- `COMPLETED`：任务完成，不等于业务采纳。

产物建议命名为：

```text
02-detailed-spec.md
```

## 4. 用户故事与功能测试 Case

### 4.1 用户故事的最小格式

```text
作为 [角色]，我希望 [动作/信息]，以便 [业务结果]。
前置条件：
成功标准：
阻断标准：
不应发生：
```

用户故事必须覆盖真实角色，而不是只按技术模块写：

- 业务操作人员：发现、核验、推进状态和处理外部结果；
- 数据治理人员：来源、清洗、去重、关联、冲突、质量；
- 经营负责人：漏斗、阻断、资源投入、价值实现；
- 管理员/验收人员：规则、权限、审计、边界和回归。

### 4.2 Case 矩阵

每个 P0 用户故事至少包含：

1. 正常成功；
2. 真实空数据；
3. 加载/处理中；
4. 接口失败；
5. 重试；
6. 重复提交/幂等；
7. 缺少上下文；
8. 身份、角色、类型或来源冲突；
9. 权限边界；
10. 任务终态和回流边界。

每个 Case 记录：对象 ID、来源、时间窗口、动作前状态、实际结果、动作后状态、用户提示、写入对象和 `PASS/FAIL/BLOCKED/OLD_RUNTIME/NOT_RUN`。

产物建议命名为：

```text
03-user-stories-and-test-cases.md
```

## 5. 需求业务角度方案审查

技术审查不能代替业务审查。业务审查要针对“用户是否会据此做出错误决定”进行挑战。

### 5.1 审查问题

- 同一个字段在不同页面是否有不同角色含义？
- 同一条记录在不同入口是否会变成不同对象？
- 系统是否把建议、推断、预测、来源事实和人工确认混为一谈？
- 用户是否知道当前该做什么、为什么不能做、需要补什么？
- 统计数字是否能解释对象、范围、时间、分子和分母？
- 失败、未知、空库和没有分母是否被误看成 0？
- 是否存在绕过人工确认或冲突闸门的入口？
- 当前能力是否被误标为 REAL？
- 这项功能是否真的减少决策时间、判断成本或业务风险？

### 5.2 审查输出

按 `P0/P1/P2` 分级：

- `P0`：会造成对象、金额、主体资格、统计或业务决策误判；不闭合不能放行；
- `P1`：影响团队协作、回流、审计、可追溯或重复使用；可受控试用；
- `P2`：尚未纳入当前目标的扩展业务；没有独立需求和验收不提前实现。

产物建议命名为：

```text
04-business-requirements-review.md
```

## 6. 方案拆解、代理分工和决策登记

跨仓库、长周期任务如果存在明显的模型能力/成本分层，除本节外还要读取 [分层模型多 Agent 闭环](multi-model-orchestration.md)，使用唯一主执行台账管理依赖、Agent、证据、P0/P1 和外部 Gate。各仓库文档、聊天进度和子 Agent 的完成声明都不能替代主台账。

### 6.1 先制定模块计划

将审查结果拆为不重叠的工作包：

| 工作包 | 输入 | 输出 | 写入边界 |
|---|---|---|---|
| 需求/边界 | 现状和冲突 | 地图、Spec、故事 | 文档目录 |
| 后端契约/状态 | Spec 和数据事实 | DTO、状态、服务规则、测试 | 后端指定文件 |
| 前端路径 | Spec 和用户故事 | 页面、工作流、文案、空态 | 前端指定文件 |
| 数据/任务 | 数据源和任务事实 | 回跑或核查计划 | 明确的脚本/SQL |
| 验证/评估 | Case 和运行基线 | 回测矩阵、体验/价值评估 | 评估文档 |

同一文件不能同时由多个代理修改。主 Agent 始终负责：

- 划分不重叠写集；
- 给代理输入、输出格式、停止条件和禁止范围；
- 合并前读取变更并做业务一致性检查；
- 代理失败/超时后决定继续、缩小范围或自己收尾；
- 最终决定是否放行。

多模型调度时，高判断力模型优先承担业务边界、跨仓契约、Spec/质量审查和放行；高吞吐模型优先承担写集清楚的实现、构建和证据采集。具体模型名不写死，按当前平台可用能力选择。

### 6.2 代理任务契约

每个代理收到：

```text
目标：
上下文/事实：
允许读取：
允许修改：
禁止修改：
必须产出：
验收条件：
停止条件：
超时后的交付格式：
```

代理应返回：完成状态、实际改动文件、证据、未完成项、风险和下一步；“我分析过了”不等于产物已经落盘。

### 6.3 决策日志

所有会影响业务含义的决定都进入 `00-decision-log.md`，至少记录：

```text
决策编号：
冲突问题：
采用方案：
放弃方案：
原因：
影响的对象/页面/API：
验证方式：
状态：已验证 / 待运行验证 / PLANNED
```

## 7. 按方案分模块实现

实现顺序优先为：

1. 数据/API 契约、对象边界和状态；
2. 统一动作闸门和错误/空态语义；
3. 页面工作流、上下文传递和提示文案；
4. 统计、日志、审计和可观测性；
5. 视觉细节和低风险体验优化。

实现时建立需求追踪表：

| 需求/故事 | Spec 条款 | 实现文件/API | 测试 Case | 证据 | 状态 |
|---|---|---|---|---|---|
| R3-P0-01 | 2.2 编号语义 | Service/DTO/页面 | TC-001 | 响应字段/页面 | |

先修“会改变业务判断”的错误，再修“看起来不漂亮”的问题。不要用 UI 禁用按钮代替服务端规则；不要用默认值、缓存或伪统计隐藏不确定性。

## 7.1 正式业务写入路径审计与唯一策略源

复杂业务系统不能只审查用户当前看得到的按钮或一条主 Service。实现前必须全局盘点所有可能改变正式业务状态的入口和回调，包括：

- 页面、批量操作、快捷入口和跨页工作流；
- Controller、Service、Mapper、定时任务和消息消费者；
- AI/异步分析完成回调、外部保存、派生产物生成/重建和跨系统同步；
- 自动创建对象、自动改变状态、关联、审批、归档和状态修正；
- 初始化脚本、数据修复脚本和后台运维接口。

检索关键词应覆盖 `insert`、`update`、`delete`、`create`、`link`、`sync`、`save`、`generate`、`rebuild`、`approve`、`archive`、`setStatus`、`setIsTracking` 以及项目自己的业务动作名称。不能因为某个主路径已经收紧，就假定旁路和异步回调也遵守同一规则。

正式产物建议为：

```text
business-write-path-inventory.md
```

可直接套用 `templates/business-write-path-inventory.md`，并与 `templates/traceability-matrix.md`、`templates/iteration-manifest.md` 一起维护需求、写入路径和跨轮回归。

每一条写入路径至少记录：

| 字段 | 要回答的问题 |
|---|---|
| 动作 | 改变了什么正式业务状态 |
| 入口 | 页面、API、任务、回调或脚本是什么 |
| 触发者 | 用户、角色、AI、系统任务还是人工运维 |
| 对象 | 影响哪些正式对象、候选对象、派生产物、状态或统计对象 |
| 写入 | 写入哪些表、字段、状态和关联关系 |
| 前置证据 | 来源、身份、类型、资格、上下文和人工确认是否足够 |
| 阻断条件 | 哪些冲突、缺失、过期或权限状态必须 HOLD |
| 唯一策略源 | 允许/阻断判断由哪个服务或策略对象统一提供 |
| 幂等 | 重复提交、重试、迟到回调会不会重复写入 |
| 审计 | 是否记录操作者、来源、时间、任务 ID、前后状态 |
| 回滚 | 错误写入如何撤销、补偿或转人工复核 |
| Case | 正常、失败、绕过前端和旁路入口如何回测 |

同一业务动作只能有一个策略源。例如“生成/重建正式产物”“改变正式状态”“把外部结果写回业务对象”不能由不同页面各自决定；页面、后台任务和 AI 回调只能调用统一的策略结果。新增入口必须同时更新写入清单、Spec、用户故事和负向测试 Case。

阶段门：

```text
存在未审计的正式状态写入路径，或同一动作存在互相矛盾的策略源：P0 HOLD，不进入业务放行。
```

## 8. 启动项目并按 Spec/Case 回测

### 8.1 运行策略

- 用户已启动服务：不自动重启；先判断当前进程是否包含改动；
- 没有热部署证据：源码结果和线上结果分开记录；
- 服务不可用：标记 `BLOCKED`，用接口、日志、静态分析或人工步骤替代，不伪造运行通过；
- 涉及写入：先确认环境、影响对象、旧数据、回滚和幂等；未获授权时只读回测。

### 8.2 证据矩阵

对数据型页面建立：

```text
页面字段/交互
→ API 请求/响应
→ Controller/Service/Mapper
→ 数据库/任务表
→ 来源/时间戳/状态
→ 用户下一步
```

每条证据标记：

- `RUNTIME_PASS`：当前运行实例已验证；
- `STATIC_PASS_PENDING_RUNTIME`：源码或配置已满足，运行进程未重载；
- `OLD_RUNTIME`：当前响应仍是旧实现；
- `PARTIAL_PASS`：主路径或部分条件通过，但关键业务条件仍未闭合；
- `BLOCKED`：因环境/权限/安全边界不能执行；
- `NOT_RUN`：尚未执行；
- `FAIL`：当前事实与预期不一致。

### 8.3 回测顺序

按模块执行：

1. 事实读取和对象边界；
2. 主体/角色/类型和证据状态；
3. AI 分析和人工确认；
4. 派生视图、操作工作台和跨页上下文；
5. 外部异步任务、终态和人工回写；
6. 统计、时间窗口和空态；
7. 权限、重复提交、失败和重试。

## 9. 交互友好性和业务价值评估

不要只记录“测试通过”。每轮都要回答两个不同问题。

每条交互结论必须标注观察来源：

- `UI_OBSERVED`：真实浏览器点击、截图或可交互 DOM 观察；
- `HTTP_OBSERVED`：接口、页面加载和网络事实观察；
- `SOURCE_INFERRED`：根据源码逻辑推断；
- `DOCUMENTED_ONLY`：只有需求或 Spec 定义；
- `NOT_EVALUATED`：当前工具或环境无法评估。

没有 `UI_OBSERVED` 时，只能输出“交互风险初评”或“待人工 UI 验证”，不能宣称真实用户体验已经通过。

### 9.1 交互友好性

按 1～5 分或高/中/低评估：

- 用户能否一眼知道当前对象和上下文；
- 状态文案是否让人区分成功、空、失败、未知和待核验；
- 阻断时是否告诉用户为什么、缺什么、下一步是什么；
- 从入口到目标动作是否少绕路；
- 页面之间的项目、阶段、来源和任务是否一致；
- 保存、重试、返回、重复提交是否有可理解反馈；
- 文案是否会诱导用户把 AI 建议当事实或审批；
- 不同屏幕、键盘/鼠标和可达性是否可用。

### 9.2 业务功能价值

按业务结果评估：

- 是否减少发现、核验、汇总和决策时间；
- 是否提高来源证据完整度和对象匹配可信度；
- 是否减少错误状态写入、错误对象创建和跨对象串线；
- 是否让下一步动作更明确、更可执行；
- 是否形成可复用的处理、分析和关联记录；
- 真实数据覆盖、有效分母和人工闭环是否足够；
- 当前价值属于 REAL、HYBRID、DEMO 还是 PLANNED。

评估必须记录“事实、判断、未证实假设”三类内容，不把主观印象写成系统成功率。

## 10. 根据评估制定优化方案

每轮回测后新增：

```text
05-backtest-and-evaluation.md
06-optimization-plan.md
```

优化方案必须引用本轮 Spec、应用地图和失败 Case，不能重新凭感觉发散。每一项优化包含：

- 问题和业务影响；
- 证据和受影响用户路径；
- 优先级 P0/P1/P2；
- 方案、模块和写入范围；
- 成功标准和回归 Case；
- 是否改变对象/状态/统计定义；
- REAL/HYBRID/DEMO/PLANNED 变化；
- 回滚或人工降级方式。

## 11. 多轮迭代协议

### 11.1 用户要求“再迭代两遍”时

执行：

```text
第 1 轮：基线建模 → 实现 → 回测 → 评估 → 优化方案
第 2 轮：按第 1 轮优化方案更新文档 → 实现 → 回测 → 评估
第 3 轮：按第 2 轮结果再次更新文档 → 实现 → 回测 → 最终评估
```

每一轮必须保留上一轮结果，不能覆盖历史证据。下一轮只处理上一轮确认的 P0/P1 问题，除非用户明确扩大范围。

### 11.2 每轮开始前

- 读取上一轮应用地图、Spec、用户故事、业务审查、回测和优化方案；
- 建立本轮变更登记和目标 Case；
- 重新确认运行实例、数据快照、脏文件和禁止动作；
- 明确哪些结果是旧运行态，哪些需要重启后验证。

### 11.3 每轮结束时

- 更新完成/部分完成/未完成/新增决策；
- 重新评估用户体验和业务价值；
- 关闭已完成的代理，保存代理交付；
- 不因为“轮数到了”而宣布通过；
- 只有 P0 证据闭合才放行，其他能力保持诚实边界。

## 12. 最终整合和交付

最终交付至少包含：

1. 结论：完成度、是否可继续使用、P0 是否放行；
2. 需求和业务地图：核心链路、对象、角色、边界；
3. Spec：状态、动作闸门、统计和空态；
4. 用户故事和 Case：已执行、未执行、阻断和失败；
5. 实现：文件、接口、数据和页面；
6. 验证：URL、命令、日志、数据库、截图或明确的缺口；
7. 交互友好性和业务价值评估；
8. REAL/HYBRID/DEMO/PLANNED 边界；
9. P0/P1/P2 待办和人工下一步；
10. 工作区、Git、重启、写入和回滚说明。

最终交接模板使用 `templates/handoff.md`，不把过程性猜测、旧截图、临时日志或未确认的“成功”写成正式完成事实。
