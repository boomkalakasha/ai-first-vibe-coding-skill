# 文档与 Git 边界

研发过程会产生两种不同的文档：帮助当前 Agent 或个人推进工作的临时记录，
以及需要随项目、团队或交付物长期同步的事实。不能因为文件放在 `docs/` 下，
就默认把它加入 Git。

## 四类文档

| 类别 | 默认进入 Git | 典型内容 | 判定依据 |
| --- | --- | --- | --- |
| `LOCAL_PROCESS` | 否 | 临时计划、Agent 工作日志、工具流水、草稿、临时截图、局部调试输出、恢复中间产物、个人偏好和机器快照 | 只服务本次本地过程，其他人不需要依赖它继续工作 |
| `DELIVERY` | 是（需在当前授权内） | 用户交付说明、发布说明、迁移/回滚手册、验收结果、面向使用者的文档 | 交付、发布、使用或回滚需要它 |
| `TEAM_SYNC` | 是（需在当前授权内） | 已确认的决策、跨 Agent/成员交接、评审结论、共享契约、团队验收矩阵 | 团队需要在不同人和不同会话之间依赖同一份事实 |
| `PROJECT_SYNC` | 是（需在当前授权内） | 项目 `AGENTS.md`、README、架构/ADR、稳定 PRD/BDD、运行和开发规范 | 项目需要把它作为长期事实源、复现依据或协作入口 |

## 提交流程

1. 写入或 `git add` 前给每份文档标注一个类别，并记录它服务的对象、持续时间和依赖者。
2. `LOCAL_PROCESS` 留在任务记录、工作区外部目录或宿主的私有记录中；不要因为“方便”把临时日志、截图、原始工具输出和恢复中间产物批量加入 Git。
3. `DELIVERY`、`TEAM_SYNC` 和 `PROJECT_SYNC` 只有在请求授权、项目规则或交付边界要求时才提交。提交前删除私人路径、凭据、机器状态和一次性调试细节。
4. 一份文档同时包含长期事实和临时过程时，拆出可同步部分；不要把整个临时台账提交上去。
5. 无法判断时保持 `PENDING`，先不 `git add`，在交付摘要中说明候选文件和缺少的判定依据。不要用全量 `git add .` 代替分类。

`.gitignore` 只能处理已经确认的本地生成模式，不能用来掩盖应该交付或团队同步的文档；增加忽略规则也要遵循项目授权和现有仓库规范。

## Review questions

- 删除本地过程记录后，团队或用户是否仍能完成交付、复现和审查？
- 这份内容是否代表项目稳定事实，而不是某次 Agent 的中间推理？
- 它是否包含必须脱敏的路径、凭据、私有运行值或真实数据？
- 这次提交是否真的需要让其他人或后续会话看到它？

只有问题的答案支持长期同步时，才把文档提升为 Git 交付物。
