# ai-first-vibe-coding skill 优化复盘（2026-07-28）

> 历史快照：本文统计固定在 2026-07-28。当前行为/触发数量和字段格式以 evals/evals.json、evals/trigger-evals.json 为准，不据本文推断最新状态。

## 1. 评估对象和依据

本次优化不是凭空设计新 skill，而是以复杂的数据驱动业务系统多轮研发任务的真实过程作为样本，比较原有 skill 的约束与实际执行中的需要。

主要依据：

- 三轮应用地图、详细 Spec、用户故事/测试、业务审查、回测和优化文档；
- 实际使用过的多代理分工、代理超时/收尾、主 Agent 合并和源码回测过程；
- 当前运行服务不重启、旧运行态、浏览器会话失效、数据库不写入和热部署不确定等真实边界；
- 原有 `SKILL.md`、跨工具适配、handoff 模板和三条 eval；
- 新增的八条行为评测和二十二条触发评测；
- 独立只读审查发现并由主 Agent 复核的旁路业务写入证据：某些在线研究保存路径可能自动创建对象/跟踪，多个页面可能各自决定地图重建。

## 2. 原有 skill 的有效部分

原有 skill 已经具备以下基础，保留并强化：

1. 先读项目规则和运行事实；
2. 服务已运行时不自动重启；
3. 保留脏工作区和用户改动；
4. 方案、实现、验证、复盘和文档对照形成闭环；
5. 数据型页面使用页面 → API → Service/Mapper → 数据库/任务表证据矩阵；
6. 从用户、数据、技术、视觉和运营五个角度复盘；
7. 通过跨工具 adapter 处理没有浏览器、数据库、热部署或子代理的情况。

## 3. 从本次实际执行发现的缺口

| 领域 | 原有缺口 | 本次证据 | 优化方式 |
|---|---|---|---|
| 任务路由 | 没有 L0/L1/L2/L3 分级 | 大任务需要三轮文档、实现和回测，小任务不应套同样流程 | 增加任务复杂度分级和复杂任务路由 |
| 需求建模 | 只有笼统“方案和边界” | 实际必须先建应用地图、业务对象、状态和边界 | 增加应用地图正式产物 |
| Spec | 没有明确业务 Spec 的最小字段 | 实际需要定义动作前置、阻断、空态、统计和回滚 | 增加详细 Spec 契约 |
| 验收 | 用户故事/测试不是强制阶段 | 真实任务需要 24 条业务 Case 区分 OLD_RUNTIME、BLOCKED、READ_PASS | 增加故事、Case、结果等级 |
| 业务审查 | 技术审查和业务审查没有拆开 | 项目编号、项目类型、招采线索误读属于业务风险而非技术 bug | 增加独立业务方案审查 |
| 代理协作 | 只有“可适度并行” | 多个代理同一轮写不同文档，部分代理超时，主 Agent 需收尾 | 增加写集、交付契约、停止条件和超时降级 |
| 业务写入路径 | 主要围绕当前页面和主 Service，未强制全入口审计 | 只读复核发现研究保存和其他页面仍可能存在自动建项/跟踪/重建旁路 | 增加正式业务写入路径清单、旁路负向 Case 和唯一策略源阶段 |
| 操作模式 | 没有显式区分只读、只方案、实现和技能评审 | 本轮评估本身需要修改 skill 资产但不能修改业务项目 | 增加 `READ_ONLY_REVIEW`、`PLAN_ONLY`、`IMPLEMENT_AND_VERIFY`、`FULL_ITERATIVE_DELIVERY`、`SKILL_REVIEW` |
| 运行证据 | 只有 REAL/DEMO/PLANNED | 源码已改但后端未重启，浏览器会话失效 | 增加 RUNTIME_PASS、PARTIAL_PASS、OLD_RUNTIME 等标准证据等级 |
| 交互证据来源 | 有视觉/交互复盘，但观察与推断混在一起 | 浏览器不可用时只能通过 HTTP 和源码代理评估 | 增加 UI_OBSERVED、HTTP_OBSERVED、SOURCE_INFERRED、DOCUMENTED_ONLY、NOT_EVALUATED |
| 能力边界 | 原有原则未包含 HYBRID | 本次大量能力真实但人工回流/持久化不完整 | 增加 HYBRID 并明确升级条件 |
| 交互评估 | 有视觉/交互复盘，但没有业务决策指标 | 需要判断用户是否知道为什么阻断、下一步是什么 | 增加交互友好性量表和阻断检查 |
| 价值评估 | 没有独立业务价值实现度 | 真实项目发现价值高，正式投标价值低 | 增加价值维度和 REAL/HYBRID 认定 |
| 多轮迭代 | 没有“再迭代两遍”的标准协议 | 本次需要轮 1 + 轮 2 + 轮 3，且不能覆盖历史证据 | 增加三轮闭环、轮次产物和停止条件 |
| 交接 | handoff 只有事实和下一步 | 复杂任务需要产物索引、需求追踪、轮次、证据和价值结论 | 扩展 handoff 模板 |
| 评测 | 原有 eval 只有 3 条行为 prompt | 无复杂任务、轻量降级和工具失效近邻样本 | 扩展行为 eval + 独立 trigger eval |

## 5. 实际验证结果

### 5.1 已通过

- 标准库静态校验通过：frontmatter 名称存在、description 长度符合、两个 JSON eval 文件可解析、关键文件无 BOM；
- `SKILL.md` 为 152 行，低于 skill-creator 建议的 500 行；
- 完整工作流拆到 reference，reference 超过 300 行并已补目录；
- 触发评测的负向样本在本次 CLI 运行中全部未触发，说明没有明显把文档、天气、图片、Excel、Git 查询等相邻任务全部吸入；
- behavior eval 已扩展到复杂三轮任务、数据链路、运行服务、skill 自身优化、轻量降级、工具缺失、业务写入路径审计和跨轮回归八类。

### 5.2 受环境限制的评测

skill-creator 自带 `run_eval.py` 在 Windows 上使用 `select()` 读取子进程管道，出现 `WinError 10038`，导致正向触发结果被误判为 0。此前 20 条触发评测得到 `12/20`，其中负向 12 条可参考，正向 8 条不能作为真实 recall 结论；后来评测集扩展为 22 条，尚未在兼容 harness 中重新取得有效分数。

单条 CLI 直测也没有按预期暴露 skill tool，而是返回了“任务内容不足”的通用答复，说明当前 `claude -p` 的命令/skill 发现方式与 `run_eval.py` 预设环境不一致。这是评测 harness 的兼容性限制，不足以否定新的 description。

官方 `quick_validate.py` 需要 `PyYAML`，当前 Python 环境缺少该依赖；已用标准库完成等价的 frontmatter、JSON、BOM 和行数校验，但没有把官方脚本结果伪报为通过。

## 6. 仍需后续验证的内容

1. 在支持 `claude -p` skill 触发协议的环境中重跑 20 条 trigger eval，并按 3 次/条计算 precision、recall 和 held-out 分数；
2. 在有可用代理/任务调度的环境中，用六条 behavior eval 做 old/new 对照，而不是只做静态审查；
3. 安装或提供 PyYAML 后执行官方 `quick_validate.py`；
4. 由用户或团队对复杂任务的输出做一次人工 review，重点检查是否流程过重、是否真的减少沟通和返工；
5. 根据真实评测反馈继续调整 description，避免为了触发率而过度吸入 L0/L1 任务。

## 7. 优化决策

本轮没有把 425 行完整流程全部塞进 `SKILL.md`，而是：

- `SKILL.md`：保留触发条件、核心原则、任务分级、执行强制点和最终交付结构；
- `references/end-to-end-workflow.md`：承载完整研发流程、文档契约、Agent 契约、证据等级、回测、价值评估和多轮迭代；
- `templates/task-baseline.md`、`decision-log.md`、`traceability-matrix.md`、`business-write-path-inventory.md`、`iteration-manifest.md`：承载任务授权、决策、需求追踪、正式状态写入审计和跨轮回归；
- `templates/handoff.md`：承载交接所需的基线、产物、追踪、证据、边界、写入审计和下一轮；
- `evals/evals.json`：承载八类行为验收；
- `evals/trigger-evals.json`：承载 9 条应触发和 13 条近邻不应触发样本。

这保持了 skill 的短上下文可用性，同时把本次工作真正形成的“文档—实现—回测—评估—再迭代”机制保存为可复用资产。
