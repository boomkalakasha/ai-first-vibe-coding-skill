# Four-layer completion gate — recovered contract

2026-09-10 reconstruction from historical PRD/BDD and D-018, not original file recovery. JSON field names and the embedded matrix format are newly reconstructed. Historical evidence does not establish the exact old CLI schema.

Run `python scripts/check_completion_gate.py templates/completion-manifest.json`, or provide a JSON object on stdin. Exit 0 / DONE_ALLOWED means all checks passed; exit 1 / DONE_BLOCKED lists issues; exit 2 / INVALID_INPUT means unreadable or invalid input. This verifies declared evidence structure, not the truth or contents of linked evidence. A reviewer must confirm that references actually demonstrate the claimed results.

Input `layers` must include SOURCE_BUILD, RUNTIME_UI, DATA_BUSINESS and RELEASE_CUTOVER. Each record is either `{"status":"PASS","evidence":[{"kind":"UI_OBSERVED","reference":"path-or-run-id"}]}` or `{"status":"NOT_APPLICABLE","reason":"specific explanation"}`. RUNTIME_PASS is also accepted. N/A needs a nonblank explanation for each layer independently. Empty evidence, unknown evidence kinds, NOT_RUN, BLOCKED, OLD_RUNTIME and DOCUMENTED_ONLY keep DONE closed.

Recognized kinds are SOURCE_INFERRED, BUILD_OBSERVED, RUNTIME_OBSERVED, UI_OBSERVED, HTTP_OBSERVED, BUSINESS_OBSERVED and RELEASE_OBSERVED. Each passing layer needs a matching kind: SOURCE_BUILD requires SOURCE_INFERRED or BUILD_OBSERVED; RUNTIME_UI requires RUNTIME_OBSERVED or UI_OBSERVED; DATA_BUSINESS requires BUSINESS_OBSERVED; RELEASE_CUTOVER requires RELEASE_OBSERVED. HTTP-only evidence cannot close a runtime layer. A screenshot cannot substitute for business correctness or a release observation. These labels organize evidence and do not establish its truth.

`acceptance_matrix` embeds the full object described in [acceptance-matrix.md](acceptance-matrix.md), and is evaluated independently; a bare claimed PASS cannot close the gate. No deployment is demanded for a task where release is inapplicable: use reasoned N/A. Default templates contain NOT_RUN and must fail until real evidence is supplied. Do not fabricate records to make the gate green.

For a bounded local-code or documentation change with no user workflow, the manifest may explicitly set `task_type` to `local_code` or `documentation`, `workflow_applicable` to JSON `false`, and `acceptance_matrix` to `{"status":"NOT_APPLICABLE","reason":"specific scope explanation"}`. All four layers are still independently checked; provide real source/build evidence and individual reasons for other inapplicable layers. Missing/unknown task scope, absent/true workflow_applicable, blank reasons or mvp_crud scope cannot use this opt-out. A completion manifest declaring mvp_crud must embed a matrix that also declares mvp_crud. Truthful task classification must be reviewed; schema checks cannot detect an intentionally mislabeled product change.

When workflow acceptance is explicitly inapplicable, at least one of the four evidence layers must still pass with matching evidence. Marking every layer and acceptance N/A cannot establish that any work was verified. This local gate validates declared evidence structure; the reviewer must verify the referenced facts.
